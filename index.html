Codexion inside

Coders sit in a ring and share one USB dongle with each neighbour. To compile, a coder needs both of its dongles at once. If it goes time_to_burnout ms without starting a compile, it burns out and the simulation ends. This page replays real runs of the program and maps how its threads, locks and heaps fit together.

    Architecture

    Threads and what they share

    There are N + 2 threads: the main thread, one thread per coder and one monitor. They share a single t_simulation. Its mutex doubles as the start gate: the main thread holds it while it creates the other threads, so none of them can start until the clock is set.

    coder.c

    A coder's life

    Each step is a timed wait on sim->cond that ends at the phase's end, at the coder's burnout deadline, or when the simulation stops, whichever comes first. Any step can return 0, and the coder thread then exits.

    dongle.c

    How a coder gets two dongles

    dongle_acquire puts one request into both neighbouring dongles' heaps, then repeats dongle_try_grant until it returns something other than 0. A coder never holds one dongle while waiting for the other, so the ring cannot deadlock.

    Each try, under sim->mutex

    1. Has the run stopped, or has my deadline passed?Give up and remove the request.
      −1
    2. Am I at the top of both heaps?If not, someone with priority is ahead of me. Sleep.
      0
    3. Are both dongles free and cooled down?If one is still cooling, wake exactly when it's ready.
      0
    4. Take both, reset my deadline, log "is compiling".Both "has taken a dongle" lines and "is compiling" print in this one locked step.
      1

    Sleeping and waking

    Between tries the coder sleeps in pthread_cond_timedwait. The wake time starts as its burnout deadline and moves earlier if a dongle's cooldown ends sooner.

    Anyone who changes the picture broadcasts on sim->cond: dongle_release when dongles go back, dongle_acquire when a request leaves the heaps, and simulation_stop when the run ends. Every sleeper then rechecks its own condition.

    One coder alone has a single dongle as both left and right. It takes it, prints one "has taken a dongle", and waits for a second that never comes, until it burns out.

    heap.c · heap_order.c · heap_storage.c

    The request heap

    Each dongle keeps a complete binary min-heap of waiting requests, built from nodes with parent, left and right pointers. Positions are numbered from 1 and the children of p are 2p and 2p + 1. That's how heap_node_at finds the next free leaf. Switch the scheduler to see how the same six requests reorder.

    PosCoderArrivalDeadline

    This is an illustration. In the program a dongle only ever has its two neighbours as requesters, so a real heap holds at most two requests. The tree code works for any size. Each insert adds a leaf and sifts it up, exactly as heap_push does. In EDF, equal deadlines fall back to arrival order.

    Synchronization

    Locks and what they guard

    PrimitiveProtectsUsed by
    sim->mutexThe result, every coder's deadline and compile count, every request heap, and printing (one line at a time). It's also the start gate.Coders, monitor, and the main thread at start-up
    sim->condNot data. It's the one place every thread sleeps: phase waits and dongle waits.coder_wait, dongle_acquire
    dongle->mutexThat dongle's in_use flag and cooldown_until. The subject requires one mutex per dongle.dongle_busy, dongle_take, dongle_release

    Lock order: sim->mutex first, then at most one dongle mutex. dongle_release updates each dongle under that dongle's mutex, unlocks it, and only then takes sim->mutex to broadcast. No thread ever waits for the big lock while holding a dongle lock, so the locks themselves cannot deadlock.

    Clean ending: the monitor prints "burned out" and sets result in the same critical section, and coder_log prints nothing once the result is no longer SIM_RUNNING. Nothing can appear after the burnout line.
